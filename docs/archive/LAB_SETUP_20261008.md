# Historical lab GPU setup (2026-10-08)

Superseded by [current setup](../LAB_SETUP.md) and [lab handoff](../LAB_HANDOFF.md).
The four-episode/custom-trainer commands below are historical pilot diagnostics.

Prepared 8 October 2026. The Docker recipe targets Linux x86-64 with an NVIDIA GPU:
native Linux Docker Engine or Docker Desktop's Linux/WSL2 backend on Windows.
It is **not yet build/GPU-qualified**: the local Docker Linux engine is unavailable.
The existing Windows Python training tests do not qualify this Linux image.

Local checks: Compose v2.32.4 accepts the configuration; container-configuration
unit tests pass. A Windows diagnostic passes runtime-version, dependency, model
import, CUDA BF16 and PyAV checks, but explicitly skips TorchCodec, EGL rendering
and persistent container mounts. Its full `passed` flag is false, as intended:
[diagnostic report](../../results/container_setup/windows_diagnostic_v1.json).

## Host requirements and boundaries

- An approved lab account, persistent SSD allocation and installation permissions.
- A compatible NVIDIA driver; `nvidia-smi` must work on the host. Do not install
  a GPU driver inside the container or replace a working lab driver without IT.
- On Linux: Docker Engine, Compose v2 and configured NVIDIA Container Toolkit.
  Docker group access grants root-level privileges: ask the administrator to
  choose the appropriate access policy rather than granting it to everyone.
- On Windows: Docker Desktop with WSL2/Linux containers and an appropriate Windows
  NVIDIA driver. Prefer a Linux-filesystem project/storage path within WSL for
  dataset I/O. Do not install the Linux NVIDIA display driver inside WSL.
- Budget 150-200 GB free persistent storage for initial SFT experiments, including
  headroom. Docker image/build cache also consumes storage on the Docker engine's
  disk, which may differ from the mounted project SSD. Plan additional image/cache
  headroom and check both locations before building; do not prune others' images.
- Confirm overnight power/sleep/reboot policy, network access and backup location.

No services or host ports are exposed. SSH/AnyDesk belong on the approved host,
not inside this training container. Use SSH over the university-approved network/
VPN where available; AnyDesk is optional, with strong authentication and approval.
On Linux, check its current Xorg/incoming-connection requirements before relying
on it. Test access from outside the lab before leaving. Do not expose Docker's
socket, Jupyter or SSH directly to the public internet.

## What the image contains

Python 3.11, CUDA-enabled PyTorch 2.10.0 / torchvision 0.25.0 (cu128), LeRobot
0.4.4, MuJoCo 3.11.0, PyAV 15.1.0, Transformers 4.57.6 and FFmpeg/EGL libraries.
Linux LeRobot also requires TorchCodec: use its 0.10.0 **CPU decoder wheel**, paired
with PyTorch 2.10; model compute remains on CUDA. Qualification scripts use PyAV,
while the default upstream trainer may use TorchCodec, so preflight checks both.

Critical versions are constrained in `docker/constraints-smolvla.txt`. The Python
base tag, OS packages and other transitive dependencies are not fully locked yet.
The build records `/opt/openarm/requirements.resolved.txt`. Once the lab build
passes, retain its image ID/digest and resolved requirements with experiment
reports; optionally pin the base image by digest using `OPENARM_PYTHON_IMAGE`.
Do not describe the initial recipe as a bit-for-bit reproducible Linux lockfile.

The image contains repository code/config/assets only. `.dockerignore` allowlists
the build context: raw data, checkpoints, virtual environments, Git metadata,
third-party checkouts and prior reports are not sent to the builder. Runtime
model downloads, Hugging Face uploads and W&B uploads are disabled. No credentials
are baked into the image. Rebuild after code changes; the running image does not
automatically track edits in the host checkout.

## 1. Prepare persistent storage

Create these directories under an **existing, approved absolute storage root**:

```text
openarm-storage/
  raw/test_collection_new_env/           # original manifest + four episode dirs
  models/smolvla_base/                  # config.json + model.safetensors
  models/smolvlm_backbone/               # pinned tokenizer + backbone config
  assets/openarm_mujoco/v1/             # pinned robot XML + meshes
  assets/capstone_automateData/          # exact recording-compatible checkout
    third_party/openarm_mujoco/v1/      # robot assets required by that checkout
  datasets/                            # LeRobot exports; read/write
  runs/                                # checkpoints, logs, reports; read/write
  cache/                               # runtime home/model/torch cache; read/write
```

The raw/model/asset mounts are read-only. Only datasets, runs and cache are
writable, plus temporary/shared-memory filesystems. All bind sources must exist;
Compose refuses to silently create missing input directories. Inputs are outside
Git and must be transferred separately, preserving bytes and checksums. Do not
copy an entire personal Hugging Face cache containing saved login credentials.

Use model revisions in `configs/smolvla_model_sources.json`. The matched collector
snapshot is `b7297ba82701fe7e7814c32ea617a85f832b74a4`; robot assets are
`161039cd74ea8675fb8197836fe5674659825c75`. The recorded file hashes remain
authoritative. Avoid line-ending conversions in the source snapshot; a mismatch
must fail, not be bypassed. The asset checkout is unnecessary for training-only
checks, but required for task rollouts and the full simulator test suite.

Copy `docker/lab.env.example` to repository-root `.env` and edit:

```dotenv
OPENARM_STORAGE=/srv/openarm-storage
OPENARM_UID=1000
OPENARM_GID=1000
OPENARM_GPU_ID=0
```

The path is an example, not permission to write to an administrator-owned folder.
On Linux/WSL, get your actual numbers with `id -u` and `id -g`. Ask the owner/admin
to make `datasets`, `runs` and `cache` writable by that account. Do not use broad
`chmod 777` or mount all of your home directory. The service runs non-root with
a read-only root filesystem, dropped capabilities and no privilege escalation.

## 2. Build and qualify

Run commands from the repository root. Build requires internet access for packages
and the base image, but no GPU. Runtime checks require the configured host GPU.

```bash
nvidia-smi
docker version
docker compose version
docker compose config --quiet
docker compose build smolvla
docker compose run --rm smolvla python scripts/container_preflight.py --output /runs/lab_preflight_001.json
```

Preflight tests pinned package versions, `pip check`, SmolVLA imports, a CUDA BF16
matrix multiplication, H.264 encode/decode via PyAV and TorchCodec, an independent
MuJoCo EGL render and writable persistent mounts. It loads no model weights and
does not execute the robot. A synthetic rendered scene/video here is only an
infrastructure probe, not new task data or a successful policy rollout.

The report's `passed` must be true with **no skipped checks**. Optional `--skip-*`
flags are diagnostic only: even when the selected checks exit successfully, the
full report remains `passed=false` if anything is skipped. CUDA success does not
imply EGL success. If WSL2 graphics interoperability fails, keep training and
rendering qualifications separate; do not claim closed-loop readiness until both
work. Never relax simulator safety limits to work around environment failures.

For build provenance after success:

```bash
docker image inspect openarm-smolvla:local
docker compose run --rm smolvla python -m pip freeze --all
```

Save those outputs using your normal experiment logging workflow. The image's
resolved requirements are also available at `/opt/openarm/requirements.resolved.txt`.
Host reboots, driver/runtime maintenance and container removal can stop jobs;
mounted checkpoints survive, but automatic job resume is not implemented here.

## 3. Verify the data and run the known training qualification

For the four-episode pilot only, use the explicit smoke selection. Do not apply
that four-episode selection to a new 100-episode release. Agree and version new
whole-episode splits and refit training-only normalization for that release.

```bash
docker compose run --rm smolvla python scripts/prepare_smolvla.py --dataset /raw/test_collection_new_env --selection configs/smolvla_collection_smoke.json
docker compose run --rm smolvla python scripts/prepare_smolvla.py --dataset /raw/test_collection_new_env --selection configs/smolvla_collection_smoke.json --export /datasets/collection_smoke_001
docker compose run --rm smolvla python scripts/verify_smolvla_export.py --dataset /raw/test_collection_new_env --selection configs/smolvla_collection_smoke.json --export /datasets/collection_smoke_001 --report /runs/readback_001.json
docker compose run --rm smolvla python scripts/qualify_smolvla_training.py --export /datasets/collection_smoke_001 --checkpoint /models/smolvla_base --backbone /models/smolvlm_backbone --output /runs/qualification_001 --steps 24
```

Use fresh export/run/report names: existing results are refused. You can stage an
existing verified export instead, but rerun readback on the lab host. The known
qualification overrides backbone paths to container paths and performs real
training/save/reload plus same-process resume checks. Do not assume Windows
checkpoint-embedded absolute paths will work on Linux. Qualification is small
and is not the full-window 100-episode training experiment.

The general upstream smoke launcher has different defaults (including float32)
and still needs separate long-run qualification. Do not infer that it has the
diagnostic script's BF16 setup, exact process-level resume or retention policy.
No claim about 4090 throughput is established by this Docker recipe. Time a
representative warmed-up training loop before booking long jobs.

## 4. Task rollout after infrastructure and training pass

With the exact source/asset bundle staged, a separate process imports the matching
environment and uses the newly saved model with container-compatible paths:

```bash
docker compose run --rm smolvla python scripts/rollout_smolvla.py --snapshot /assets/capstone_automateData --episode /raw/test_collection_new_env/train_00003 --checkpoint /runs/qualification_001/final_checkpoint/pretrained_model --backbone /models/smolvlm_backbone --output /runs/policy_rollout_001 --max-steps 100 --prefix 5
```

The tiny Windows-trained checkpoint collided before grasp. This command is an
interface/safety diagnostic, not a promised success. For local scene regression:

```bash
docker compose run --rm smolvla python -m unittest discover -s tests -v
```

This suite includes the preserved older two-blade scene as well as training-boundary
tests; it does not replace matching-v3 task evaluation. Cross-OS physics and exact
GPU resume behavior require requalification, not an assumption of bitwise equality.

## 5. Remote jobs and persistence

For a bounded diagnostic that survives an SSH/AnyDesk disconnect, use a detached
one-off container (no `--rm`, so its logs/exit status remain inspectable):

```bash
docker compose run -d --name openarm-qualify-001 smolvla python scripts/qualify_smolvla_training.py --export /datasets/collection_smoke_001 --checkpoint /models/smolvla_base --backbone /models/smolvlm_backbone --output /runs/qualification_detached_001 --steps 24
docker logs -f openarm-qualify-001
docker inspect --format '{{.State.Status}} {{.State.ExitCode}}' openarm-qualify-001
```

Closing the log viewer does not stop the detached job. Confirm the actual exit
code and saved report; merely seeing a container start is not a pass. There is no
automatic restart policy that might rerun a job into an existing output directory.
Keep jobs sequential initially, and coordinate GPU use with others.
